Objekty na haldě zaujímají paměť. Kdo ji uvolní? V C++ to dělá programátor ručně — a zapomene-li, nastane **memory leak** (únik paměti). V C# tuto práci přebírá **garbage collector** (GC).

---

## Jak GC funguje

Garbage collector automaticky prochází objekty na haldě a hledá ty, na které **neexistuje žádný odkaz** — jsou nedosažitelné. Takové objekty bezpečně uvolní.

```csharp
void Metoda()
{
    List<int> seznam = new List<int> { 1, 2, 3 };
    // seznam je na haldě, odkaz je na zásobníku
}
// Metoda skončila → odkaz ze zásobníku zmizel
// → GC může seznam uvolnit
```

GC neběží po každém přiřazení — spouští se v době, kdy systém potřebuje uvolnit paměť. Programátor to obvykle neovlivňuje a ani nemusí.

> 💡 Ruční volání `GC.Collect()` je v běžném kódu anti-pattern — GC ví lépe, kdy je vhodný čas.

### Generace (0, 1, 2)

GC nekontroluje celou haldu pořád — to by bylo pomalé. Místo toho dělí objekty do **generací** podle stáří:

- **Generace 0** — čerstvě vytvořené objekty. Kontroluje se nejčastěji, protože většina objektů žije jen krátce (lokální proměnná, dočasný výsledek) a rychle se uvolní.
- **Generace 1** — objekty, které přežily kontrolu generace 0. Kontroluje se méně často.
- **Generace 2** — dlouhožijící objekty (statická data, cache, objekty žijící celou dobu běhu programu). Kontroluje se nejméně často.

Objekt, který kontrolu přežije (protože na něj stále vede reference), postoupí do vyšší generace. Princip za tím: čím déle objekt už žije, tím pravděpodobněji bude žít i dál — nemá smysl takové objekty stále znovu prohledávat, takže GC šetří čas tím, že se věnuje především čerstvým (generace 0) objektům, kde je šance na úklid nejvyšší.

## Dispose pattern a IDisposable

GC uvolní **paměť**, ale neumí uvolnit jiné zdroje — otevřené soubory, databázová připojení, síťové sokety. K tomu slouží vzor **Dispose**.

Třída, která drží systémový zdroj, implementuje rozhraní `IDisposable`:

```csharp
public interface IDisposable
{
    void Dispose();
}
```

Voláním `Dispose()` zdroj explicitně uvolníte — nemusíte čekat na GC.

## Blok `using` — automatické Dispose

> 💡 S blokem `using` jste už prakticky pracovali v kapitole **Vstupní a výstupní proudy** — tam šlo o praktické pravidlo "obal StreamReader/StreamWriter do using". Teď víte proč: `using` volá `Dispose()` z rozhraní `IDisposable`, které jsme právě představili.

Blok `using` zavolá `Dispose()` automaticky na konci bloku, i při výjimce:

```csharp
// Bez using — musíte volat Dispose ručně (a nezapomenout)
StreamReader sr = new StreamReader("soubor.txt");
string obsah = sr.ReadToEnd();
sr.Dispose();  // co když před tímto řádkem nastane výjimka?

// S using — Dispose se zavolá vždy
using (StreamReader sr = new StreamReader("soubor.txt"))
{
    string obsah = sr.ReadToEnd();
}  // tady se automaticky zavolá sr.Dispose()
```

`using` lze použít na jakoukoli třídu implementující `IDisposable` — `StreamReader`, `StreamWriter`, `SqlConnection`, `HttpClient` a další.

### Zkrácený zápis (C# 8+)

```csharp
using StreamReader sr = new StreamReader("soubor.txt");
string obsah = sr.ReadToEnd();
// Dispose se zavolá na konci aktuálního scope (metody, bloku)
```

## Kdy používat `using`

Kdykoli pracujete s třídou implementující `IDisposable` — a to bez výjimky. Poznáte ji tak, že má metodu `Dispose()` nebo Visual Studio ji zvýrazní.

Nejčastější třídy vyžadující `using`:

| Třída | Zdroj |
|---|---|
| `StreamReader`, `StreamWriter` | Soubory |
| `SqlConnection`, `SqlCommand` | Databázová připojení |
| `HttpClient` | Síťová připojení |
| `Graphics` | GDI+ grafický kontext |
| `Bitmap`, `Image` | Obrázky v paměti |

## Shrnutí

| Pojem | Vysvětlení |
|---|---|
| Garbage collector | Automaticky uvolňuje nedosažitelné objekty z haldy |
| Generace (0, 1, 2) | GC dělí objekty podle stáří, aby nemusel prohledávat celou haldu pořád |
| Memory leak | Objekt v paměti, na který neexistuje odkaz, ale GC ho ještě neuvolnil — v C# vzácné |
| `IDisposable` | Rozhraní pro třídy držící systémové zdroje |
| `Dispose()` | Explicitní uvolnění zdroje |
| `using` blok | Automaticky zavolá `Dispose()` i při výjimce |

## Otázky k zamyšlení

1. Podle čeho garbage collector pozná, že objekt "už nikdo nepotřebuje"? Proč nestačí počítat reference?
2. Co jsou generace (0, 1, 2) a proč GC prohledává mladé objekty častěji než staré?
3. GC uvolňuje paměť, ale ne soubory, síťová spojení či databáze. Proč? K čemu slouží `IDisposable` a `using`?

## Procvičení

### Řešený příklad

**Zadání (teoretické):** Kolega tvrdí: "V C# nemusím nic řešit, garbage collector uklidí všechno." Uveďte dva konkrétní scénáře, kdy toto tvrzení neplatí a program má problém i s fungujícím GC.

<details markdown="1">
<summary>💡 Zobrazit řešení</summary>

**Scénář 1 — nespravované prostředky:** GC spravuje jen paměť .NET objektů. Otevřený soubor, databázové spojení nebo síťový socket jsou prostředky operačního systému — GC o nich "neví" a hlavně *neví kdy* je uvolnit (běží nedeterministicky, klidně za minuty). Program, který otevírá soubory bez `using`/`Dispose`, je drží zamčené a může vyčerpat systémové limity dřív, než GC vůbec poběží.

**Scénář 2 — nechtěně držené reference:** GC uklízí jen **nedosažitelné** objekty. Pokud program přidává objekty do statického `List`u (cache, log, registrace událostí) a nikdy je neodebírá, jsou objekty stále dosažitelné → GC je uklidit *nesmí* → paměť roste donekonečna. To je memory leak v jazyce s GC — ne proto, že by GC selhal, ale protože program objekty pořád "chce".

Shrnutí: GC řeší otázku *"kdy je bezpečné uvolnit paměť"*, ne otázky *"kdy vrátit prostředky OS"* a *"kterých objektů se má program vzdát"*. Ty zůstávají na programátorovi.

</details>

### Samostatná cvičení

1. **Základní** — Najděte ve svých programech tři místa, kde používáte `using`, a u každého napište, jaký prostředek se tím uvolňuje.
2. **Pokročilejší** — Napište program, který otevře soubor `StreamWriterem` bez `using` i bez `Close`, a pokuste se stejný soubor otevřít znovu (nebo smazat v průzkumníku). Popište, co se stalo, pak opravte přes `using`.
3. **Bonus (*)** — Prostudujte vzor události jako zdroje úniku: dlouhožijící objekt A se přihlásí k události objektu B a nikdy se neodhlásí. Proč B (a vše, co drží) nemůže být uklizeno? Napište minimální ukázku.
